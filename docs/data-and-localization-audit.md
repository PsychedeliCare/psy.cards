# Data provenance, localization and review audit

Audit date: 19 September 2026. Audience: maintainers, scientific reviewers and translators. The public companion is [Sources & methods](https://psy.cards/sources).

## Delivery and boundaries

This change refreshes the submodules, introduces a mechanically checked source registry, and publishes an English sources page. Existing translations, the Wikipedia import and iOS data packs are preserved. The integrity repairs, translation metadata, scientific approval records and architecture changes below are a **proposed roadmap**, not implemented review guarantees.

Four languages remain public: English, French, German and Italian. The target is the [24 official EU languages](https://european-union.europa.eu/principles-countries-history/languages_en), with GitHub as the review and publication record. The agreed future publication policy permits content with explicit review status; reviewed print editions are separate immutable releases.

### Registry contract and maintenance

- [Source catalog](../packages/shared/sources/catalog.mjs): editorial provider roles, imported field inventory, transformations, differences between consumers, and limitations. Update it when a consumer begins or stops using a field.
- [Generated registry](../packages/shared/data/sources.json): schema version 1; provider IDs, descriptions, roles, source links, separate repository/article revisions, data-change dates, retrieval dates, and per-file SHA-256 hashes plus last-modifying commit links. Missing scientific review dates are `null`, with `reviewStatus: "not-recorded"`.
- `pnpm sources:refresh` regenerates the registry from local inputs and Git history; `pnpm sources:check` compares it with those inputs. Both work without network requests. `pnpm build` runs the check first. A direct package-only Astro build bypasses this root check; publication should use the root command.
- `pnpm sources:test` exercises provenance behavior with temporary repositories. No translation or review data is generated by these commands.

For subsequent updates: fetch the submodules, inspect the semantic diff, select their commits, then run `sources:refresh`, `sources:check`, tests and the root build. Commit the changed gitlinks and registry together. Ordinary builds never fetch upstream HEAD. Uninitialized submodules, missing inputs or missing history fail explicitly. CI must initialize submodules and fetch sufficient history to identify each file's last modification; use a full-history checkout and unshallow submodules where necessary.

For **local content edits**, commit the input files first, then refresh and commit the registry. The generator rejects uncommitted input bytes because they cannot honestly inherit a prior commit's date. Keep both commits in the same review branch. Do not use a build timestamp as a substitute for provenance. Source refresh does not record a new retrieval time for a historic snapshot.

Provider file lists include all imported local JSON and glossary files. The registry is a declaration of actual consumers, not a claim that every field in a loaded JSON blob is displayed or independently validated. The catalog distinguishes loaded-but-unused fields from displayed/exported fields. Code changes still require review of that inventory; the checker does not infer field usage from arbitrary application code.

### Provider roles

TripSit supplies factsheets, pair statuses/notes/citations, status definitions, upstream labels and disclaimer HTML. Combogen supplies selection/order and presentation mappings. Local overlays supply translated text, UI copy and class descriptions. Locally curated SMILES have no original per-entry source recorded; do not retroactively attribute them to PubChem or another database.

Wikipedia supplies slang and search enrichment, not safety status. PsychonautWiki effect names and URLs are inherited through TripSit's `pweffects`; Erowid and publications are linked references, not independently synchronized providers. The Drugs Wheel is credited for classification inspiration. Drugwatch is acknowledged but has no separate importer. SmilesDrawer is rendering software, not a chemical database. The repository package's ISC declaration and the saved Wikipedia CC BY-SA 4.0 declaration are recorded as such; unknown declarations remain unknown.

## 2. Current translation storage and audit

### Data flow and precedence

1. `drugs/` provides canonical substance records, interactions, English and translated labels, and disclaimer HTML. `combogen/config.json` selects 25 visible columns from 31 interaction keys; the full factsheet file contains 555 records.
2. `packages/shared/i18n/ui/{locale}.json` holds interface copy. `content/{locale}/` holds label augmentation, combo notes, definitions, class descriptions and per-substance overlays. Most text units use `{ "_source": "English", "text": "localized" }`; labels/UI use ordinary strings. Glossaries are Markdown files.
3. On web, `load-locale.ts` eagerly imports the four languages and all drug overlays. Local drug labels override upstream labels; a DXM alias bridge is applied. Factsheet overlays replace text recursively, including English overlays, without checking `_source`. Missing factsheet overlays leave upstream content. Class descriptions are separate fallback copy.
4. `combos.ts` reads either direction of a pair and prefers the requested direction's available fields. It looks up translated notes using display-column order. `definitions.ts` prefers translated definitions, then upstream definitions and unknown fallback. Disclaimer HTML falls back to English. Missing UI messages return the key, not English text.
5. The native generator separately implements merges, aliases, grouping, status resolution and projection. It exports flattened `.strings` files and full per-locale JSON packs. It uses alphabetically sorted translation pair keys, unlike the web. This duplication already produces different behavior.

## 3. Enrichment and ranking

### Existing Wikipedia behavior

The saved import contains 47 entries, 231 search documents and 13 unresolved terms. Its source block records the article revision and retrieval timestamp. The importer supports a live MediaWiki fetch, a file/URL, or stdin. It cleans wikitext, maps terms using curated mappings and TripSit keys/labels/aliases, expands resolved substance sets into pairs, and builds lookup indexes. It includes an excluded-name list and a manual Hippie flip entry.

The current importer is not fully reproducible: it uses live HEAD by default, adds wall-clock timestamps, seeds mappings from its previous output, embeds manual curation in code, retains no raw snapshot, and assigns IDs using row positions. Class mappings can expand broad terms to multiple drugs. A mapping's `exact`/`class`/`unresolved` label describes entity resolution, not the quality of scientific evidence.

`combo-slang.ts` restricts card names to entries with exactly the two requested keys or a single mapped pair. The first retained slang name wins; intoxication names are used only if no slang names exist. Search indexes broad and multi-pair rows without the same restriction. This can associate a name with more specific pairs than the original row establishes. The first roadmap repair is to require reviewed mappings before promoting such aliases; unresolved and broad candidates remain in a review queue, not silently discarded.

### Reproducible import specification — proposed

1. **Fetch once, pin once:** request an explicit revision through [MediaWiki's revisions API](https://www.mediawiki.org/wiki/API:Revisions). Save raw wikitext, article identity, revision ID/time, retrieval time, attribution/license reference and SHA-256. For a latest-version update, first resolve HEAD, then pin that returned ID.
2. **Separate inputs:** maintain reviewed term maps, exclusions and manual additions outside generated output. Each manual addition records author, rationale, source and review state. Keep safety content in the TripSit/canonical editorial layer.
3. **Stable identity:** introduce maintained entry IDs with a migration map from existing row IDs. Use normalized row content as a matching aid, never row position as identity. Ambiguous matches require human reconciliation; edited content creates a new revision of the same confirmed entry.
4. **Deterministic derivation:** record importer version/commit, mapping version, source checksum and configuration. Sort generated keys and indexes, retain source order only where editorially intended, and separate retrieval-event timestamps from derived artifact bytes. Re-running frozen inputs must be byte-identical.
5. **Review the delta:** report added/removed/changed labels, mapping changes, unresolved terms and affected pair IDs. Empty tables, schema changes, duplicate identities and ambiguous broad mappings must fail or enter an explicit queue; never overwrite the last usable snapshot on failure.
6. **Publish deliberately:** generation and ordinary builds read pinned local inputs only. Review PRs approve the precise enrichment diff and attribution. Test exact mappings, class mappings, row reorderings, deletions and repeated runs from fixtures.

The same adapter contract applies to future providers: immutable input + attribution → validated normalized records + provenance → reviewed enrichment. Adding another provider does not grant it authority to replace safety classifications.

### Actual ranking heuristics

| Surface | Current rule |
| --- | --- |
| Columns | Local group order: antidepressant, stimulant, empathogen, psychedelic, dissociative, depressant, opioid, cannabinoid. Preserve combogen's original order within each group. Overrides classify cannabis, MDMA, opioids and tramadol. |
| Default search/common previews | Curated order: amphetamines, cocaine, caffeine, MDMA, LSD, mushrooms, ketamine, alcohol, GHB/GBL, benzodiazepines, cannabis. Substance cards then expand to remaining configured columns. |
| Web search | Fuse.js `threshold: 0.34`, `includeScore: true`, `ignoreLocation: true`; relative weights: title 0.48, aliases 0.34, keywords 0.20, subtitle 0.08, typeLabel 0.05. These weights are not percentages. |
| Final web results | Retrieve 24 Fuse candidates; stably promote normalized exact title/alias matches within those candidates; deduplicate by destination URL; show 12. Non-exact candidates retain Fuse order. The `featured` field is populated but is not used for ranking. |
| Matched-term explanation | Separate from result ranking: exact match 100; prefix 80 minus 0.01 × term length; query starts with term 60; substring 40; ordered-character match 20; shorter terms break score ties. |
| Native search | Lowercased substring match against search terms or canonical key; preserves substance order. No Fuse ranking. |

These are editorial/navigation choices, not measured prevalence, safety, or evidence confidence. The roadmap should centralize/version policy and add a small multilingual relevance fixture before changing ranking. Search normalization currently strips non-ASCII letters after decomposition; Greek/Cyrillic text is especially affected.

## 4. Glossary and translation provenance — proposed

### Canonical terminology

Retain Markdown tone/style guidance, but move approved terminology into a structured glossary keyed by stable concept IDs such as `pharmacology.serotonin-syndrome`. Each concept has an English definition, domain, references and optional do-not-translate rule. Each locale record has preferred wording, accepted alternatives, prohibited/ambiguous terms, context, rationale and review history. Substance aliases/slang are language/region-tagged concepts rather than literal translations of English nicknames.

Locale maintainers approve terminology through PRs; scientific reviewers approve definitions or meaning changes. Never give existing glossary rows an invented validator. Build a reverse index from concepts to translation units so a changed preferred term reopens only affected reviews. Preserve a history of glossary revisions and store the relevant concept hashes with each translation; an unrelated glossary edit should not invalidate all languages.

### Translation-unit identity and records

Use stable domain keys, for example `interaction:lsd|mdma:note`, `substance:lsd:summary`, `effect:<concept-id>:label`, and `ui:search.placeholder`. Canonicalize aliases and pair ordering before assigning IDs. Do not use English text, array positions, translated labels or route order as identity.

Keep plain application text separate from an authoring/provenance sidecar so existing readers can migrate incrementally. The proposed sidecar contains:

| Group | Required information |
| --- | --- |
| Identity | Unit ID, locale, domain, source locale, risk classification, context and placeholder schema. |
| Source | Canonical source value/hash; provider revision and field pointer; hashes of dependencies such as status, dosage values and evidence references. |
| Translation | Exact text/hash; state (`unknown`, `draft`, `reviewed`, `stale`); generation method (`human`, `machine`, `imported`, `unknown`). |
| Generation | Provider/model when known; generated-at time; prompt/schema version; relevant glossary hashes; input/output hashes and retained output. Null where unavailable. |
| Attribution | Contributor GitHub identity and contribution PR/commit; language reviewer, review time, reviewed source/translation hashes and authoritative GitHub review reference. |
| History | Append-only generation, edit, approval, rejection, staleness and withdrawal events. Superseded text remains recoverable. |

Hash canonical serialized values with a versioned normalization rule. Preserve numeric meaning, punctuation that changes meaning, negation, placeholders and markup. A source dependency change invalidates approval even when the translated sentence itself is unchanged. Deleted units become retired/tombstoned, not silently reassigned.

Store model outputs to reproduce a publication; provider/model/prompt identifiers alone cannot guarantee identical inference. Queue missing or changed units, cache by source hash + locale + relevant glossary/prompt/provider versions, preserve human edits, and record unsuccessful jobs separately. Require explicit provider selection and job limits when automated translation is introduced.

Migration must preserve text byte-for-byte initially. Mark legacy provenance unknown, compute present-day hashes, and record migration time separately from generation/review time. Equal English/localized wording is not automatically a failure. Quality checks compare expected keys, source drift, placeholder schemas, markup, numeric invariants and glossary usage, with explicit exceptions for legitimate unchanged proper nouns.

## 5. Sustainable scientific and language reviews — proposed

### GitHub workflow

1. **Prepare an update PR.** Include old/new provider revisions, semantic changes by stable unit ID, cited evidence, affected translations, unresolved enrichment, and rendering previews. Routine updates can be proposed weekly by a future workflow; urgent source corrections use the same process immediately. No scheduler is installed by this change.
2. **Triage scientific impact.** Classify changes to doses, timing, interaction status, warnings, evidence and class-level generalizations. Separate editorial spelling/formatting from meaning. An automated classification is an aid; a reviewer owns the decision. Local class descriptions and chemistry records need evidence just as upstream-derived claims do.
3. **Review science.** Designated scientific reviewers record approve/request-changes/unresolved decisions, rationale, limitations, evidence references and exact unit/dependency hashes. Preserve distinctions between studies, case reports, mechanistic inference and other evidence; do not turn citation count into an evidence score. Re-check external evidence when a reviewer discovers an update/retraction and record its inspected version or access date.
4. **Review language.** Locale reviewers examine the approved or clearly labeled draft source, glossary and rendered context. Record language approval separately. An edit changing meaning returns to scientific review; language approval never upgrades an unreviewed scientific claim.
5. **Enforce at the PR boundary.** A maintainer-managed reviewer registry maps real GitHub identities to scientific/locale roles. CODEOWNERS routes reviews, but does not by itself require both roles. A required check verifies the applicable role decisions against exact content hashes and authenticated GitHub review IDs; repository protection dismisses stale PR approvals and blocks bypass by ordinary contributors. Contributors cannot self-declare trusted approval in JSON.
6. **Publish and archive.** Generate the release from committed, hashed inputs. Copy authenticated decisions into append-only records, retaining PR/review links. Preserve review records for unchanged units when unrelated PR files change; new changes to a unit reopen its approval. A merged PR alone is not a per-claim scientific approval.

The same person can hold multiple qualifications, but record the scientific and language decisions as separate events. Require independent review of the contributor's own safety-content changes. Actual reviewer identities and branch-protection settings must be configured when this roadmap is implemented; no identities or approvals are assumed here.

### Publication policy

| State | Meaning | Future public behavior |
| --- | --- | --- |
| Unknown | No reliable generation/review history. | May publish with “review not recorded”; never display a validated badge. |
| Draft | New/edited source or translation awaits an applicable review. | May publish with explicit scientific and language states and source version. |
| Reviewed | Applicable reviews bind to the current text and dependencies. | Display reviewer attribution, scope/date and links to the review record. A language approval alone does not imply scientific review. |
| Stale | Previously associated source, evidence, glossary dependency or translated meaning changed. | Reopen affected reviews. For safety translations, display current English with a clear language/status indicator until updated; retain old text in history. |

Unchanged units retain approval when only a provider's repository commit changes. Code-only upstream changes must not invalidate every translation. Contradictory or withdrawn claims require a maintainer's explicit correction/withdrawal decision rather than leaving a stale “reviewed” badge. Track scientific and linguistic states independently even when the UI summarizes them.

### Reviewed releases, print and corrections

Tag immutable dataset releases and store a manifest with source revisions/checksums, schema and generator versions, content/translation/glossary hashes, approval records, published locales and output checksums. Reviewers work against a named release/PR snapshot while updates continue in other branches. Apply returned reviews only to matching hashes; rebase by unit, preserving unaffected approvals and flagging conflicts.

Print editions require scientific and language sign-off for all included safety units, plus layout checks. Each print run records its release ID; QR destinations expose both the edition's context and current corrections. Never silently edit an archived release. Keep an errata log identifying affected editions/units, reason, replacement text, reviewer and replacement release. For an urgent correction, a designated maintainer may publish a clearly marked draft correction immediately, retire affected downloadable print artifacts, open expedited review, and record the decision. Do not relabel unrecalled printed copies as updated.

## 6. Scaling to 24 languages

### Measured baseline and implications

The pre-change root production build succeeded in about **3.2 seconds**, with 321 HTML pages, 1,201 JSON files, **106,690,975 bytes of HTML** (~107 MB decimal), and a **1,443,902-byte search bundle** (~1.44 MB decimal). Total JavaScript was 4,401,534 bytes; the combo-data bundle was 1,035,460 bytes. These are emitted, uncompressed bytes, not a measured browser transfer or timing benchmark. The English native JSON pack occupies 284,779 bytes; all four packs occupy about 1.2 MB on disk.

At 25 columns, there are `25 × 24 / 2 = 300` unordered pairs per language. Twenty-four languages yield **7,200 pair JSON routes**, plus HTML/print routes. Locale-specific data grows roughly linearly with language count; pair coverage grows quadratically with substance count. Expanding to all 555 upstream records would be a fundamentally different scale and is not part of this plan.

Static generation remains suitable for the curated collection. At unchanged page shapes, locale-proportional HTML would approach six times today's volume; that is a projection, not a measured 24-language build. The main concerns are repeated HTML/card markup, whole-dataset JavaScript imports, and PWA caching of every language, not the size of translation JSON itself. The current service worker broadly precaches HTML/JSON/assets and also caches content by unversioned URL, so release consistency matters as well as storage size.

### Staged architecture

| Stage | Implementation direction | Acceptance criteria |
| --- | --- | --- |
| 1 — Integrity | Repair roots/checking and non-destructive extraction; canonicalize substance/pair/effect identities; fix consumed-field coverage and web/native mismatches. | Missing files fail. Repeated extraction preserves translations. Pair order/aliases and source array reorders cannot select the wrong text. Both consumers agree on shared safety fields. |
| 2 — Shared publishing | Move source normalization and overlay resolution into `packages/shared`; introduce one versioned locale registry and provenance sidecars; generate web/native adapters from the same resolved dataset. Retain English root URLs and existing slugs. | One new locale entry drives tooling/routes/worker/PWA/native support. Missing TripSit translations fall back explicitly to English. Preview locales do not become public automatically. |
| 3 — Delivery | Build compact per-locale search documents and lazily load them; remove upstream JSON and all-language loaders from browser imports. Separate shared numeric/chemical data from localized text. Cache shared shell plus the selected locale, with optional language downloads and release-scoped cache names. | Adding inactive languages does not grow active-locale search payload or automatic offline download size. A release switch cannot mix old notes/statuses with new provenance. Set performance budgets from measured representative mobile loads. |
| 4 — Language readiness | Preserve Unicode letters/numbers in search; use locale-aware comparison and carefully reviewed alias normalization. Test Greek/Cyrillic fonts and Latin extensions, grammatical/plural categories, longer copy and placeholders. | Greek/Bulgarian queries survive normalization; Polish/Romanian plural examples pass; German/Finnish expansion fits cards and print. Dates and numbers display appropriately without converting clinical dose units. |
| 5 — Reviewer readiness | Implement glossary/provenance records, incremental queues, GitHub role checks, status-aware publication and immutable releases. | Source-only, evidence-only, translation-only and unrelated updates invalidate exactly the intended approvals; stale safety translations visibly fall back. |

The target locale set is `bg, cs, da, de, el, en, es, et, fi, fr, ga, hr, hu, it, lt, lv, mt, nl, pl, pt, ro, sk, sl, sv`. All official EU languages use left-to-right scripts; broader European coverage may later require RTL support. Separate locale/language from country-specific services or regional slang.

String Catalogs are the recommended Xcode 15+ localization workflow. Xcode 26 generated symbols are a separate typed-access layer on top of String Catalogs. Assess generating native UI catalogs from the shared message source, including plural variants and named-to-positional argument mapping; do not make Xcode-extracted strings a competing authority for shared safety content. Keep `.strings` compatibility during migration. Test locale display under `en_US`, `de_DE`, `ar_SA` and `ja_JP` as useful formatting probes, without treating them as new publication languages.

No database, CMS, hosted translation platform or server rendering is required for the current scale. Introduce such services only if review volume or editing requirements justify them; Git remains the auditable publication record.

## 7. Validation and follow-up checklist

Current delivery: check provider revisions against submodule HEADs; compare all input hashes; verify deterministic registry generation and failure on absent files/history; build the site; inspect mobile/keyboard disclosure behavior; verify all four footer links use the canonical English destination, including event pages. Do not count the current `i18n:check` exit code as translation validation.

Roadmap test fixtures must cover: missing/empty locale data, identical proper nouns, failed provider responses, placeholder/number changes, array reorderings, both pair directions, DXM/GHB aliases, broad slang mappings, import row reorderings, source deletion, glossary dependency changes, conflicting concurrent PRs, review spoofing, stale approval dismissal, native/web parity, and atomic offline release updates. Print acceptance includes named-release rendering and visible long-language layout checks.

Implement stages as independently reviewable changes. Stage 1 is the prerequisite for safe bulk regeneration; locale launches require stages 2–4 and explicit editorial readiness. Stage 5 can then formalize reviewed release claims. Until then, preserve the honest public statement: **psy.cards review history is not recorded**.
